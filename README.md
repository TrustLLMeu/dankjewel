## Dankjewel — Online Evaluation System for LLM-Generated Text

A modular, multi-dimensional evaluation framework based on the TrustLLM project
protocol (D7.5) for assessing the quality of text generated by Large Language
Models. All four evaluation prongs are implemented; measurements that lack the
evidence to compute are reported as `unknown` rather than as a fake score (see
[Score Aggregation](#score-aggregation)).

**License:** Apache 2.0 — see [LICENSE](LICENSE)  
**Project:** TrustLLM (EU Grant #101135671)  
**Lead:** Lars Bungum, NTNU

---

### Architecture Overview

The system is built on a **four-pronged evaluation approach**, each analyzing a
different dimension family of generated text:

| Prong | Name | Method | Status |
|-------|------|--------|--------|
| **1** | LLM-as-Judge | Sentence embeddings (MiniLM) + toxicity classifier (toxic-bert); default backend `embeddings`, with an optional 0.5B local LLM judge as a dual-output track (`tiny_judge`) | ✅ Complete |
| **2** | Rule-Based | Lexicon/heuristic scoring (validated for English; 8 further Germanic lexicons are unvalidated translations) | ✅ Complete |
| **3** | Extraction-Based | spaCy triple extraction + offline Wikidata fact-checking (122-entity seed KB, labeled as a seed) + deterministic claim admission + optional 1.5B atomic-claim track, MiniCheck verifier and LLM admission (`llm_extract`, `llm_verify`, `llm_admit`) | ✅ Complete |
| **4** | Intrinsic | Model log-probabilities from vLLM (perplexity, uncertainty, entropy) | ⚠️ Requires logprobs — without them all Prong 4 dimensions are `unknown` |

A FastAPI server (`src/api.py`) with a single-page HTML5 frontend
(`frontend/index.html`) supports interactive generation (vLLM or any
OpenAI-compatible remote API) and real-time evaluation with streaming output.

### Installation

#### Standard install (CPU only — no GPU required)

```bash
pip install -r requirements-minimal.txt
python3 -c "import nltk; nltk.download('vader_lexicon')"
python3 -m spacy download en_core_web_sm
python3 scripts/build_wikidata_db.py
uvicorn src.api:app --host 0.0.0.0 --port 8080
```

Open **http://localhost:8080**. All four prongs are available:

- **Prongs 1–3** run locally on CPU with no external dependencies.
- **Prong 4** works via any remote OpenAI-compatible backend that returns
  per-token logprobs (OpenAI, Groq, Fireworks, etc.) — supply a Base URL and
  API key in the UI's Backend Selector. If the provider does not return
  logprobs, Prong 4's dimensions are reported as `unknown` placeholders and
  excluded from the prong and total scores; the other three prongs
  are unaffected.

> **Local vLLM server** (`requirements.txt`, CUDA GPU required) is only needed
> if you want to run generation *on your own machine* rather than via a remote
> API key. Any OpenAI-compatible server works, including llama.cpp on CPU —
> set `VLLM_BASE_URL` (and `VLLM_API_KEY` when the server requires a key).

**Python 3.12+ required.**

### Quick Start

#### CLI Example

```bash
python3 main.py
```

Evaluates 4 sample texts across all prongs and saves results to
`evaluation_results/evaluation_results.json`.

#### Web UI (generate + evaluate)

```bash
# Terminal 1: start a vLLM server (or skip if using a remote API key)
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-1.5B-Instruct --port 8000

# Terminal 2: start the IE server
uvicorn src.api:app --host 0.0.0.0 --port 8080
```

Open **http://localhost:8080** in your browser. From there you can:

- Pick a backend: **Local (vLLM)** or **Remote (OpenAI-compatible, bring-your-own-key)**
- Configure generation parameters (temperature, top-p, penalties, max tokens)
- Generate text with real-time SSE token streaming
- View all 4 prong scores with expandable per-dimension breakdowns
- Export results as JSON / browse evaluation history (localStorage)

#### Evaluate-only (no generation, no vLLM)

```bash
curl -X POST http://localhost:8080/evaluate \
  -H "Content-Type: application/json" \
  -d '{"prompt": "What is the capital of France?",
       "text": "The capital of France is Paris."}'
```

#### Python API

```python
from src.pipeline import EvaluationPipeline

pipeline = EvaluationPipeline(enable_prongs=[1, 2, 3, 4])
result = pipeline.evaluate(
    text="The capital of France is Paris.",
    prompt="What is the capital of France?",
    lang="en",
)
print(result["aggregated_scores"]["total_score"])
```

### Evaluation Dimensions

#### Prong 1 — LLM-as-Judge

| Dimension | Method | Notes |
|-----------|--------|-------|
| **Relevance** | Cosine similarity (MiniLM embeddings) to prompt | `unknown` when no prompt is supplied |
| **Semantic Coherence** | Sliding-window sentence embedding similarity | |
| **Reliability** | Topic-stability (embedding variance) | |
| **Toxicity** | unitary/toxic-bert classifier | `agg_value = 1 − toxicity` |

Prong 1's default (and current) backend is `embeddings`: MiniLM cosine
similarity plus toxic-bert classification. No generative LLM judge runs —
the family name follows the D7.5 protocol. Evaluate results record the
backend in `metadata.prong1_backend`. With `tiny_judge` on, the judge is
routed by language (details in [docs/MULTILINGUAL_JUDGE.md](docs/MULTILINGUAL_JUDGE.md)):
English uses the 0.5B (`DANKJEWEL_JUDGE_BASE_URL`), other languages use the
1.5B (`DANKJEWEL_JUDGE_BASE_URL_NONEN`, model `DANKJEWEL_JUDGE_MODEL_NONEN`),
and the Relevance metadata records `judge_route` ("en" | "non-en") plus the
served `judge_model`.

#### Prong 2 — Rule-Based (prototype language configuration)

| Dimension | Method | Notes |
|-----------|--------|-------|
| **Fluency** | Flesch readability (language-adapted formula) | |
| **Politeness** | Lexicon cue count (+0.1/cue, −0.1/rude cue, clipped to [0,1]) | |
| **Emotional Intensity** | VADER sentiment + punctuation features | `aggregate=False` |
| **Formality** | Formal/informal lexicon markers | |
| **Hedging** | Modal verbs & uncertainty cues | `aggregate=False` |
| **Lexical Diversity** | Type-token ratio over word tokens (worked example in `docs/EXTENSIBILITY.md`) | `aggregate=False` |

Language support: English is the validated prototype. Lexicons exist for
eight further Germanic languages (da, de, fo, is, nb, nn, nl, sv) as
unvalidated translations — treat scores in those languages as experimental.

#### Prong 3 — Extraction-Based

| Dimension | Method | Notes |
|-----------|--------|-------|
| **Factual Accuracy** | spaCy triple extraction → offline Wikidata verification | |
| **Factual Consistency** | Cross-claim contradiction detection via Wikidata QIDs | |
| **Temporal Accuracy** | Date anchor extraction → Wikidata P585/P580/P582/P569/P570/P571 | |
| **Comparative Factuality** | JJR/JJS comparative claims → Wikidata | |
| **Modality Awareness** | Hedged vs. asserted claim fraction | `aggregate=False` |

**Claim pipeline.** Extraction proposes candidates; only admitted claims are
shown, counted and verified. Two tracks feed it: deterministic spaCy triples and
the optional 1.5B atomic-claim track. Markdown is cleaned first, then sentence
gates drop headings, questions, imperatives and meta-discourse, and triple gates
drop pronouns without a resolved referent, malformed triples, encyclopedic
definitions, text-deictic subjects and duplicates. Quoted propositions and
`Claim:`-labelled sentences are extracted as mentioned claims (`source="quote"`)
so teaching prose does not turn its examples into commentary. The ablation on the
exported teaching-prose fixture: 76 raw candidates → 28 after markdown → 17 after
sentence gates → 8 after triple gates → 9 with the use-mention pass, while the
hand-labelled junk falls from 46 to 2 and all five intended false-claim examples
survive. The optional LLM admission classifier (`llm_admit`, off by default) drops
two genuine claims on the same fixture, so it is documented as an experiment
rather than a default. See [docs/CLAIM_ADMISSION.md](docs/CLAIM_ADMISSION.md),
[docs/LEXICON_VALIDATION.md](docs/LEXICON_VALIDATION.md) and
[docs/EXTERNAL_EVALS.md](docs/EXTERNAL_EVALS.md).

#### Prong 4 — Intrinsic (requires vLLM logprobs)

| Dimension | Method | Notes |
|-----------|--------|-------|
| **Uncertainty** | 1 − mean token confidence | `agg_value = confidence` |
| **Perplexity** | exp(mean NLL) | `agg_value = 1/(1+ppl)`, displayed raw |
| **Token Entropy** | Shannon entropy of token distributions (normalized) | `aggregate=False` |
| **Semantic Entropy** | Entropy of top-k cluster (normalized) | `aggregate=False` |

Without per-token logprobs, Prong 4's dimensions are reported with
`status="unknown"` — placeholder values for display only, excluded from
the prong and total scores.

### Score Aggregation

Each enabled prong produces a score in [0, 1] as the mean of its `aggregate=True`
dimensions. Dimensions marked `aggregate=False` (Emotional Intensity, Hedging,
Token Entropy, Semantic Entropy, Modality Awareness) are reported but excluded
from the score — they have no universal "better" direction.

For dimensions whose raw scale is not [0, 1] / higher-is-better (Toxicity,
Uncertainty, Perplexity), an `agg_value` supplies an orientation-corrected
bounded value used during aggregation.

Dimensions whose evidence is missing (no prompt for Relevance, no verifiable
claims in Prong 3, no logprobs in Prong 4) are scored with
`status="unknown"`; failed computations are `status="error"`. Both are
reported per-dimension but never enter prong or total averages — a missing
measurement does not look like a middling 0.5. A prong with no scored
dimensions is omitted from the total, and if nothing was scored at all,
`total_score` is JSON `null` and `metadata.coverage` is `"none"`.

The total score is a weighted average of prong scores (default: 0.25 each),
renormalized if any prong is missing or errors out.

#### Choosing weights

The four presets (Equal, Factual QA, Safety, Fluency) are **exploration aids**:
they reweight the same four prong scores, and the UI labels them "explore".
Equal is the default because it makes no assumption about downstream risk.
The presets have not been validated against user judgments; treat a preset
score as a scenario and check it against your own data. The custom-weights
control lets you test a weighting without editing code. Guidance for a real
deployment: derive weights from the failure costs of your application (for
example, a factuality-critical assistant should raise Prong 3), record the
choice, and re-check it when the prong implementations change.

### Latency and hardware

Measured with `scripts/measure_latency.py` (1 cold + 5 warm calls per track, each
track in a fresh process so cold loads are real) on 2026-11-14, `feature/d75-v2`:

**Host:** Intel Xeon Gold 6132, 56 CPUs, 755 GB RAM, Python 3.12.3, torch 2.15.0+cu132,
`CUDA available=False` — CPU-only.

`POST /evaluate` (in-process TestClient; prompt “What is the capital of France?”):

| Track | Cold (incl. model loads) | Warm median | Warm p95 |
|-------|--------------------------|-------------|----------|
| baseline (all flags off) | 9.2 s | 672 ms | 684 ms |
| + 0.5B judge (`tiny_judge`) | 9.5 s | 770 ms | 783 ms |
| + 1.5B claims (`llm_extract`) | 9.7 s | 908 ms | 946 ms |
| + MiniCheck verifier (`llm_verify`, not engaged) | 9.3 s | 654 ms | 678 ms |
| all three on | 9.2 s | 1,008 ms | 1,049 ms |
| verifier engaged (KB-unknown claim) | 11.1 s | 827 ms | 946 ms |

Direct model calls (1 cold + 20 warm):

| Model | Cold (incl. load) | Warm median | Warm p95 |
|-------|-------------------|-------------|----------|
| judge, Qwen2.5-0.5B-Instruct (OpenAI-compatible) | 268 ms | 76 ms | 85 ms |
| claims, Qwen2.5-1.5B-Instruct (OpenAI-compatible) | 220 ms | 211 ms | 213 ms |
| verifier, MiniCheck-Flan-T5-Large (in-process) | 6.4 s | 196 ms | 206 ms |

Notes: the cold `/evaluate` cost is dominated by the embedding, toxicity and spaCy
loads (~9 s) that every track pays; MiniCheck adds its ~6.4 s load only when the
verifier actually runs. On the fully KB-confirmed test text `llm_verify` never
fires, so its cost is reported separately in the “verifier engaged” row.
`/generate-and-evaluate` is not measured here: no generator with logprobs is
available on this host. The JSON/Markdown artifacts are
`evaluation_results/latency_baseline.{json,md}`.

#### Robustness and throughput

`scripts/eval_robustness.py` exercises the failure cases and records what the
interface does; the table is regenerated into
`evaluation_results/robustness.{json,md}`. On the measurement host (2026-11-16):
empty input evaluates without a crash (10 of 19 dimensions scored, the rest
`unknown`); a ~21k-character input evaluates and deduplicates to one claim;
Dutch input scores with the Dutch lexicon; a judge server on a dead port yields
`judge_status=unknown` with the embedding baseline kept; a claims server on a
dead port keeps the spaCy track and records one `llm_errors` entry. Verifier load
failure, malformed model JSON and per-call timeouts are covered by the test
suite (named in the report). Throughput is sequential: 93 evaluations per minute
by default (mean 645 ms, p95 660 ms) and 76 per minute with all optional tracks
on (mean 787 ms, p95 1,263 ms); concurrent throughput needs multiple workers and
is not measured.

### Benchmarking (FEVER 2.0)

Prong 3 has been benchmarked on the FEVER 2.0 *fixers* development set
(1,174 claims). Key results:

| Condition | Coverage | Binary AUC | Conditional AUC |
|-----------|----------|------------|-----------------|
| Seed DB (~122 entities — a small seed, not Wikidata) | 0.3% | 0.497 | n/a (0 covered REFUTES) |
| Oracle DB (FEVER-targeted) | 8.7% | 0.538 | 0.682 |

Coverage (fraction of claims where Wikidata returned CONFIRMED or DENIED) is
the primary bottleneck — uncovered claims are reported as `unknown`
(excluded from scoring, not treated as a neutral 0.5).
The seed row is re-measured on the current pipeline (2026-11-14, expanded
seed DB): the earlier 9.0% / 0.494 figures predate the qualifier gates that
now abstain on unverifiable embedded details, and the modest Nordic/TrustLLM
seed expansion does not cover any additional FEVER fixers entities (identical
4/1174 covered on the old and new seed).
See [DB_EXTENSION_GUIDE.md](DB_EXTENSION_GUIDE.md) and `scripts/eval_fever2.py`
for details.

#### Verifier benchmark (SciFact)

A second, independent benchmark for the MiniCheck verifier
(`lytang/MiniCheck-Flan-T5-Large`): SciFact (Wadden et al., EMNLP 2020), public
and ungated. Pairs are evidence-annotated SUPPORT/CONTRADICT claim–sentence
pairs; NOT_ENOUGH_INFO claims carry no labelled evidence and are excluded.
This validates the verifier *component*, not the seed-KB path.

| Split | n | Accuracy @0.5 | AUC | Mean latency | p95 latency |
|-------|---|---------------|-----|--------------|-------------|
| dev | 338 | 0.601 | 0.835 | 258 ms | 367 ms |
| train | 957 | 0.555 | 0.790 | 232 ms | 340 ms |

Reading: the ranking signal is strong (AUC 0.835 on dev) while accuracy at the
0.5 cut-off lags — MiniCheck is conservative on scientific text. The 0.8/0.2
bands are calibration-sensitive and should be checked per domain.
`scripts/eval_scifact.py` regenerates both rows; provenance
(source URL, file hashes, model) is in `evaluation_results/scifact.json`.
LLM-AggreFact, the intended second benchmark, is gated on HuggingFace and could
not be fetched.
